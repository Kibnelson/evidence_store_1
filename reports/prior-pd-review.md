# Earlier PD runs and reusable evidence

## Routing and replay

The earlier `docs_8k_v1` runs used one producer and three decoders on separate GPUs, TP=1, a fixed model and output budget, and the exact same saved prompts, history, request order, and arrival offsets. The published 20-conversation runs use 20 warm-up requests and 156 measured requests per run. Keep those prompt-token and arrival receipts, warm-up boundaries, real device IDs, and effective launch arguments in the new Faiss replay format. Use the earlier workload as a smoke fixture and run the new datasets through their own replay manifests. [Phase 2 run card](../../context_pilot_paper/docs/evidencestore/implementation/scheduler_v2_phase2_native_and_three_modes_run_card.md#workloads-and-common-engine-settings)

Native and Full Blend make P issue a one-token request to return native KV transfer coordinates. The proxy selects D by round robin after P responds, forwards the coordinates, and relays the decoder stream. The proxy records both engine IDs and the request attempt. The GPU-retention variants additionally use conversation affinity. Record selection time and affinity explicitly because moving D selection earlier or changing stickiness changes queue time and cache availability. [Native proxy](../../context_pilot_paper/scripts/scheduler_v2_phase1_native_pd_proxy.py#L389) · [Full Blend flow](../../context_pilot_paper/docs/evidencestore/implementation/scheduler_v2_phase2_native_and_three_modes_run_card.md#full-blend-flow-and-pressure-behavior)

The earlier 2P/2D fixture forces all four P→D combinations and records actual worker IDs. Its cache settings differ by P as part of the fixture. Reuse its route validation with the new per-role cache budgets and launch settings. Keep cluster-specific Slurm setup in the launch layer. ## What the old counters establish

Full Blend captured completed `totalBytes` per NIXL handle before freeing it and joined those handles to the request. Native 1P/3D used pre/post aggregate deltas for the NIXL histogram `_sum` and `_count`. Those capture completed transport payload. They give a cross-check for the new per-request collector, which also needs submission, terminal outcome, retries and partial completion, and independent physical-link measurements. [Prior byte accounting](../../context_pilot_paper/docs/evidencestore/implementation/scheduler_v2_phase2_five_modes_20_docs8k.md#67-how-we-measure-the-kv-sent)

The old resource sampler gives per-GPU utilization at about 100 ms resolution. That is useful for finding load imbalance. Add scheduler token counts and sampled model-runner GPU timings for granular compute. Keep CPU timing, GPU active time, and data transfer spans as separate measurements because their work can overlap. [Prior resource sampler](../../context_pilot_paper/scripts/scheduler_v2_phase1_native_1p3d_docs8k.py#L506)

The earlier Full Blend versus retention results vary routing, cache lifetimes, reconstruction and verification, and instrumentation. Use them to check expected flows and counter units. For the new experiment, compare the same method, worker layout, and routing policy before and after the handoff change.
